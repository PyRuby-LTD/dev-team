# ADR-001 How activity data leaves the watch

Status: **decided - do not proceed**, 2026-09-25
Reopens when the Garmin Connect Developer Program accepts new applications
Date: 2026-09-25
Owner: architect

## Context

on-track needs activity data from a Garmin watch without the athlete connecting
it to a computer. This decision gates every story in EPIC-001.

Constraints carried in: costs borne by on-track, ceiling GBP 10 per user per
month and must fall with scale; Strava permanently excluded on commercial
terms; on-track is Python on GCP Cloud Run, scales to zero, public REST API.

## Options

### A - Garmin Connect Activity API (direct)
Push or ping on activity completion, FIT files, backfill, per-user OAuth. Free.
Precisely this feature.

**Strava is the working proof.** Its Garmin sync is this API: the user
authorises it once, usually from inside Garmin Connect under Connected Apps -
which is why customers do not remember granting OAuth - and Garmin pushes each
completed activity to the partner within a couple of minutes of the watch
syncing. Distance, time, heart rate and route transfer; Garmin-exclusive
wellness metrics such as Body Battery do not. The subscription is all-or-nothing
on activity types, which corroborates A8: the transport takes everything and
on-track discards what is not a run.

**Closed.** Garmin stopped processing new Developer Program applications around
spring 2026 - the access request form was withdrawn, applicants were told new
Health, Activity, Training, Courses and Women's Health requests are paused with
no timeline, during a programme redesign that followed Strava's litigation over
API terms. Existing integrations continue. Connect IQ is unaffected.

### B - Connect IQ app or data field on the watch
No API exists to read saved activity files. `ActivityRecording` creates
recordings; `FitContributor` writes fields into a FIT during an activity;
neither reads a completed one.

A data field can, however, capture the activity live and post it itself -
`makeWebRequest` is available to foreground data fields from API 5.0.0, over
WiFi or bridged via the phone.

Costs: background services are capped near 32k memory; `makeWebRequest` returns
`-403` below roughly 3kB free; no request queuing; `-104` without a phone
connection; `BLE_REQUEST_TOO_LARGE` on oversized payloads. An hour at 1Hz is
~3,600 samples, ~70-80KB with position, heart rate and cadence - too large to
buffer, so it must stream during the activity.

Yields our own data rather than Garmin's FIT, and requires the athlete to run
the data field.

**Revised after further research: this is the highest-fidelity route still
open, not the lowest.** `Toybox.AntPlus.RunningDynamicsData` exposes filtered
instantaneous cadence, ground contact time, ground contact balance, vertical
oscillation, stance time percentage and step length; `Activity.Info` is handed to
a data field's `compute()` each second. Every input on on-track's list -
including splits, which we would derive ourselves from per-second data, and
ground contact time, which Apple Health does not carry - is reachable.

It is also the only route whose door is open: the Connect IQ programme is
unaffected by the Developer Program pause. The costs are engineering, not
access. **Priority spike.**

### C - Aggregator (Terra, Rook, Spike)
Garmin data via their pre-existing partner status. Works today.

Rook: $399/mo for 750 active users - about $0.53/user, well inside the ceiling
at scale. The floor is the problem: $399/mo from day one, roughly GBP 16 per
user at 20 beta users and about GBP 300/mo before any revenue. Fails at beta
scale, passes comfortably later.

### D - Mobile app reading Apple Health / Health Connect
Garmin Connect syncs activities to Apple Health automatically. An on-track
mobile app reads workouts and posts them.

Covers every iPhone user regardless of watch vendor - this answers Q8. Costs
about GBP 80/yr for the Apple developer programme and GBP 20 once for Google,
both of which on-track incurs anyway once it has an app.

**Never produces a FIT file.** HealthKit exposes a defined set of workout types;
Garmin's proprietary FIT fields map poorly or not at all. No historic backfill.

### E - Unofficial Garmin Connect client
Works today, returns real FIT files, costs nothing. Requires holding the user's
Garmin credentials and sits against Garmin's terms, while Garmin is actively
litigating over exactly those terms.

Defensible for the customer's own account. Not a foundation for a commercial
product, and slice 2 must not depend on it.

## Blocking question

Options B, C and D never deliver a FIT file to on-track's existing endpoint.
`problem.md` states this work ends "when the FIT file reaches the API" and A8
assumes the transport need not understand file contents. Both fail under the
only affordable routes.

**Does on-track need the file, or the activity?** Product owner's decision. If
the file is required, option A is the only route and it is closed, in which case
there is no commercial answer today and we wait for Garmin.

## Consequence being designed for regardless

A source adapter boundary in front of on-track's ingest, so that an unofficial
client now and an official Activity API webhook later are interchangeable.
Reusable across that switch: the ingest contract, delivery state, retry and
scheduling, normalisation. Not reusable: credential handling and the polling
loop, since push replaces poll. Roughly two thirds.

## Risk recorded

A future Garmin webhook arriving at a Cloud Run instance scaled to zero may time
out before Python is up. Not a blocker and not worth a warm instance yet.
