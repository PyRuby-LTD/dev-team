# ADR-002: Managed Markdown persistence

Date: 2026-10-04. Status: implemented in the controlled STORY-002 session.
Customer instruction: `play story ./workspace/stories/STORY-002.md`.

Use the existing strict YAML parser with additive optional version-one storage
fields: revision, execution, history and manual_edit. Existing records remain
readable as revision zero and acquire storage metadata on their next managed
write. Do not invent workflow enrollment for planning records. This implements
the storage portion of ADR-001; its remaining runtime proposals stay deferred.

Serialize managed writers using Linux/POSIX flock on a stable workspace lock.
Validate and allocate under that lock. Compare both loaded revision and SHA-256
of the complete original UTF-8 file. Write/fsync a same-directory temporary file,
recheck the original, atomically replace, and fsync the directory. Creation uses
a no-overwrite hard link to publish a complete file. No database or sibling item
state is added; the lock and orphan temporary files are not authoritative records.

Pause persists import baseline and protected-field digests in front matter.
Resume validates the edited document and relationships, preserves narrative and
extensions, appends an import event, increments revision and removes an old
dispatch correlation. Supported edits retain execution/history, identity,
progress and permission bookkeeping. Malformed or protected-field edits remain
blocked. Correlation metadata is a storage contract, not an implementation of
response deduplication, workflow transitions or external execution recovery.

Execution failure and evidence persist independently of business state.
History/evidence commit in the same replacement as the changed record. A directory
sync error after replacement can lose acknowledgement; reload to establish what
committed before retrying. No blind retry or external exactly-once claim follows.

The supported filesystem boundary and uncooperative-editor race are documented in
[schema guidance](../../docs/backlog-schema-v1.md). No power-loss, network-filesystem
or multi-item atomicity claim is made. The unavoidable race between final comparison
and rename requires cooperation with pause/edit/resume.

[STORY-002 evidence](../evidence/STORY-002.md) maps acceptance criteria to reproducible
fault, concurrency, manual-edit and restart fixtures, covering the storage subset
of V1/V5/V6/V7. Later workflow/controller checks remain the dependent stories' work.
