# ADR-001: Markdown authority and a local workflow coordinator

Status: proposed technical design; confirmed customer constraints recorded below.
Date: 2026-10-02. Owner: architect. Scope: harness discovery/analysis first slice.
This ADR does not authorise implementation or mark the technical design accepted.

## Context and accepted facts

`../brief.md` is the authoritative customer record. It confirms Markdown front
matter as the sole work-item state, Python-controlled named outcomes, exactly
one agent/human owner per workflow step, discretionary agent consultation,
repeated analysis/human exchanges, explicit customer play and separate release.
The customer rejects dependence on a local database. The current commission is
analysis/backlog creation. No hosting provider is confirmed.
The team proposes that captured work belongs to human:customer and requires an
explicit `analyse` action before dispatch. That first-slice control remains a
proposal, distinct from the customer's confirmed owner-only workflow correction.

The inspected prototype stores state.json, mutates it directly, hard-codes stages,
and advances investigation into implementation. Its existing runner therefore
cannot safely serve as the first-slice discovery workflow unchanged.

## Proposed decision — pending review

Use one local Python coordinator per workspace, a validated Markdown repository,
immutable versioned owner-only workflow definitions, portable role/engine adapters,
and a TUI submitting commands to the same coordinator. Pin workflow versions per
item. Keep authoritative dispatch intents, human requests, decisions, execution
metadata and transition history in item front matter. Derive views in memory.

Use revision plus whole-file digest checks and atomic replacement for managed
writes. Support manual editing through pause/edit/validate/resume; atomic rename
alone cannot prevent races with an uncooperative editor. Persist intent before
invocation; deduplicate accepted transitions by response/dispatch identity.
Treat started attempts with no accepted response as uncertain after restart.
Reconcile before retrying any potentially side-effecting invocation. Exactly-once
external execution is not claimed.

Initial identity proposal: trusted local operator using filesystem permissions;
no remote authentication service. This is an assumption, not a settled customer
auth decision. Reuse the current Python direction and adapter concept; do not
select new third-party services or parsing dependencies in this ADR. Engine
providers and permissions require explicit configuration and data review before
future real dispatch. Product context and the selected team charter must reach
every adapter regardless of product directory or engine choice.

Basic metadata follows the PO's proposed `type`, `state` and `authorisation`
contract; runtime metadata is an extended-schema proposal, with no competing
kind/step/play fields. The illustrative discovery flow ends at ready-to-play.
STORY-009's play command records scoped authorisation and displays authorised work
awaiting unavailable delivery capability; it creates no delivery dispatch. Verify
its guards using a fake/guarded successor in acceptance fixtures only. Real
implementation is deferred; release remains another explicit gate. No legacy
pipeline fallback is proposed. Measurable invariants and proposed evidence are
recorded in `../qualities.md`, without unconfirmed performance/SLO targets.

Legacy import is included in the planned first slice: read-only preview followed
by explicit apply, with original files preserved as historical evidence. Detailed
stage/history/evidence mappings still need agreement. Ambiguous legacy state
cannot establish readiness, play or release; repeated import must be idempotent.

## Options considered

| Option | Assessment |
| --- | --- |
| Retain authoritative state.json or introduce a database | Conflicts with confirmed Markdown authority; rejected by constraints |
| Store durable queue/dispatch truth separately from items | Creates competing authority and cross-store commit gaps; avoid |
| Single local coordinator with file-backed state | Proposed smallest boundary consistent with the brief; requires disciplined editing/recovery |
| Distributed scheduler/service | No demonstrated scale or availability need; adds coordination and deployment cost; defer |
| Agents directly set arbitrary next state | Defeats named-outcome validation and customer gates; reject |

## Consequences and verification

Human-readable, portable state remains inspectable without a running service.
Whole-file rewrites/history growth, single-coordinator throughput and explicit
manual editing discipline are costs. Per-item atomicity does not give multi-item
transactions. Engine execution may be ambiguous after a crash; operator recovery
is an intentional capability, not a promise of exactly-once delivery.

Validate duplicate/stale responses, unincremented manual edits, repeated question
rounds, corrupt front matter, missing workflow versions, context delivery across
adapters, crash boundaries, no agent dispatch before explicit analyse, safe legacy
import, and explicit play against only a guarded/fake successor. Do not claim existing
prototype tests or execution establish these guarantees. Assumptions, open
decisions and story proposals are in `../analysis/architect.md`; detailed contract
and demonstration are in `../architecture.md`. No research/adoption decision or
cloud deployment commitment is part of this ADR.
