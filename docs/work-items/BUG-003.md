type: bug
title: Items waiting for the checkout deadlock each other
workflow: default
step: publish
depends_on: [STORY-026]

Two items that both need the checkout can wait on each other forever. Each sees the checkout sitting on the other's `devteam/<id>` branch, sees that the other is at a checkout-using step, and reports "waiting for <other>, which holds the checkout". Neither is running, so neither ever lets go.

## Cause

Dispatch gives the single checkout slot to an item that is about to be refused the checkout, and in doing so blocks the item that actually holds it.

`Runner.dispatch` (`devteam/runner.py`) walks `pending()` in a fixed order and calls `claim` for each item before any worker thread has finished. `claim` makes the first checkout-using item the single `checkout_user` and tells every later one "waiting for <first>, which is using the checkout". The first item's worker then runs `take_checkout`, finds another item's branch checked out whose current step still uses the checkout (`checkout_holder`), raises `Waiting` and releases `checkout_user`. The next dispatch pass repeats exactly the same order. The item that really holds the checkout (its branch is checked out, so it needs no switch) is always claimed second and always told to wait for the item that cannot proceed. Neither runs. No step has failed.

## Analysis

Re-checked against `devteam/runner.py` on `devteam/STORY-026`, including the customer's answers, which replace the earlier "failed holder" theory.

The customer's report matches the sequence above: STORY-026 was at `test` and held the checkout; STORY-021 was moved to `implement` and showed "waiting for STORY-026"; STORY-026 then moved to its next checkout-using steps (`sync` after `test`, then `verify`; both use the checkout), its branch still checked out, and it reported waiting for STORY-021; 021 stayed waiting on 026. There was no failure (Question 1), and only the TUI was running (Question 2).

What the code does today:

- `uses_checkout` is true for check steps, the `merged`/`abandon`/`sync` harness actions and branch-role steps. `checkout_holder(branch)` returns the item owning the checked-out `devteam/<id>` branch if its current step uses the checkout, whether or not it is running or even runnable.
- `take_checkout` returns at once when the item's own branch is checked out, so the true holder never waits on anyone at that point. The only thing that stops it is `claim` seeing another item's `checkout_user`.
- Items are dispatched in `scan().valid` order. An item earlier in that order that must switch away from a held checkout therefore starves the holder every pass. Whether the holder escapes depends on thread timing, so the stall can look intermittent.
- `sync` repeats the holder test inline against the current branch, with different wording from `take_checkout` ("which holds the checkout" versus "which holds the checkout at step ...").
- A failed item is a separate matter and not what the customer reported. `checkout_holder` ignores `_failed`, and `tests/test_abandon.py::test_dirty_tracked_and_untracked_fail_hold_checkout_and_retry` asserts that a failed `abandoning` item keeps the checkout. The customer's answer to Question 5 is that a failed item stays marked failed and keeps the checkout, so that behaviour stays and `tests/test_abandon.py` does not change. A failed item is not dispatched again until restart or `retry`, and its old waiting text stays displayed because `_waiting` is only cleared on success; that stale text is wanted fixed.
- `claim` runs `dependency_wait` before `checkout_user`, so an item blocked by an unfinished `depends_on` and with no branch yet is not claimed and cannot take the checkout. This must not regress. `dependency_wait` returns `None` for an item that already has a branch; per the answer to Question 4 no new rule is wanted there, because a dependent story cannot be moved to implement before its dependency is done.
- Challenge finding addressed: `sync` (`devteam/runner.py` 75-90) fails on a dirty tree before its holder test, so an item at `sync` behind a dirty failed holder would be marked FAILED instead of waiting. Decision: reorder so the holder test comes first in `sync`; criterion 10 is narrowed to the no-holder case (criteria 3, 9, 10 updated).
- Existing tests touching the wording: `tests/test_runner.py::test_only_checkout_steps_hold_checkout` (asserts "holds the checkout at step <step>") and `tests/test_abandon.py` line 105. Both already use the `take_checkout` wording and keep passing.

Assumptions taken from the answers:

- The checkout is owned by a single `Runner` (Question 2: only the TUI is used). Cross-process protection is out of scope.
- A queued item part-way through its machine steps (finished `implement`, waiting for `test`) keeps the checkout, so nothing switches the branch between its steps. The checkout is released when the item reaches a step that does not use it (a human-managed step such as pull-request), fails, or is done or abandoned. This matches epic 008 and Question 3's answer: waiting items start when the checkout is released at a human step, not when the PR merges.
- Fix direction: an item that cannot take the checkout because another live item holds it must not occupy the single `checkout_user` slot, so the holder can proceed. `take_checkout` and `sync` use one shared holder rule and message. A failed item keeps the checkout (Question 5); only its stale waiting text is cleared.

## Desired behaviour

- The item whose branch is checked out and whose checkout step is next runs first. Items that would have to switch away wait for it and never block it, regardless of their order in the backlog.
- An item whose step is running keeps the checkout; others wait and the branch is not switched.
- A failed item shows no stale "waiting for" reason.
- A failed item keeps the checkout and stays marked failed, as today (Question 5). Others wait for it, naming it as holding the checkout; its branch stays for inspection or `retry`. This change does not release it.
- When several items wait and the checkout becomes free, exactly one proceeds at a time. An item blocked by an unfinished `depends_on` is never the one chosen.

## Acceptance criteria

1. Reproducing the reported deadlock: item A sorts before item B. B's branch is checked out and B is queued at a checkout-using step (for example `verify`) after finishing an earlier checkout step. A is queued at a checkout-using step and has no branch checked out. Dispatching repeatedly, B runs and finishes that step, and A does not run while B still holds the checkout. B never reports waiting for A, not even briefly. Both the `sync` step and a check step such as `verify` are covered as B's step. The outcome must not depend on thread scheduling: the test fixes the order of claims so that it fails reliably before the fix.
2. Once B moves to a step that does not use the checkout (such as a human step), A takes the checkout on a later pass without a restart.
3. Failed holder: B takes the checkout, its step fails leaving uncommitted changes (the usual case), B is marked failed. A, at a branch-role step and separately at `sync`, waits with "waiting for B, which holds the checkout at step <step>" and is not marked failed; nothing is switched. This holds whether the tree is clean or dirty. `test_dirty_tracked_and_untracked_fail_hold_checkout_and_retry` is unchanged and passes.
4. After B fails, B is no longer shown as waiting for anything, even if it showed a waiting reason before it ran.
5. A failed item keeping the checkout does not stop it being retried: after `retry`, B runs on its own checked-out branch without waiting for A.
6. While an item's step is running on its own branch, a second item that wants the checkout waits, the branch is not switched, and the message names the running item.
7. With three or more items waiting and the checkout free, only one starts; the rest remain waiting until the checkout is released: the running item reaches a step that does not use the checkout (such as a human step), or is done or abandoned. A failure does not release it. Nothing switches the branch between that item's consecutive checkout steps (for example `implement`, `test`, `sync`, `verify`).
8. With three items waiting, where item 3 has `depends_on` item 2, item 2 is not `done` and item 3 has no branch yet, item 3 is never the one that takes the checkout, while items 1 and 2 (independent of each other) are eligible. Once item 2 is `done`, item 3 becomes eligible.
9. `take_checkout` and `sync` use the same holder rule and one message for a queued or failed holder, "waiting for <id>, which holds the checkout at step <step>", with no duplicated inline test. In `sync` the holder test comes before the clean-tree test, as it already does in `take_checkout`, so an item at `sync` waits for a live or failed holder whatever state the tree is in. The `claim` message "waiting for <id>, which is using the checkout" is kept for an item whose step is currently running (criterion 6).
10. The guard against switching away from uncommitted changes is unchanged when no other item holds the checkout: `take_checkout` still waits with the uncommitted-changes message, and `sync` on its own branch or on a free checkout still fails with "uncommitted changes" as today. It only yields to the holder test (criteria 3 and 9) when another item holds the checkout.
11. Any test asserting the old shorter `sync` wording is updated to the single message in criterion 9. `test_only_checkout_steps_hold_checkout` and `tests/test_abandon.py` keep passing unchanged. The rest of the suite still passes.

## Implementation

Implemented the checkout scheduling fix in `devteam/runner.py`. Before reserving
`checkout_user`, claim now checks whether another queued or failed item owns the
checked-out branch. Dependency checks still run first; running workers retain the
existing "which is using the checkout" message. A shared `checkout_wait` rule
supplies the holder message to claim, take_checkout and sync. Sync checks the
holder before checking cleanliness. Successful claims clear the previous waiting
reason, so expected and unexpected failures do not retain stale waiting text.
Failed items continue to hold their branch and can be retried.

Added six unit/component tests in `tests/test_checkout_queue.py`, using real local
git repositories and runner transitions. Worker starts are deferred until all
claims finish for deterministic queue tests; an event controls the running-worker
case. No journey suite was added.
