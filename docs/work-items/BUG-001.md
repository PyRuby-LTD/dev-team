id: BUG-001
type: bug
title: Answer dialog truncates long question text
workflow: default
step: publish
---
In the terminal UI, the dialog for answering questions shows each question as a single clipped line, so a long question cannot be read in full.

## Cause (suspected)

`Answers.compose` in `devteam/tui.py` renders each question in a `Label`, which sizes itself to its content and is clipped by the dialog rather than wrapping. `questions.parse` joins continuation lines into one long string, which makes this worse.

## Analysis

What exists today:

- `Answers.compose` (`devteam/tui.py:223`) yields `Label(Text(f"{number}. {question.text}", "bold"), classes="question")` inside a `VerticalScroll` inside `Vertical(classes="dialog wide")`.
- CSS (`tui.py:351-358`): `.dialog` is `width: 70; max-width: 90%; height: auto; max-height: 85%`, and `.dialog.wide` is `width: 100`. `.dialog VerticalScroll` is `height: auto; max-height: 30`. `.question` only sets `margin-bottom: 0`.
- Cause, established from the Textual 8.2.8 source: `Label` passes `shrink=False` to `Static`, so `get_content_width` returns the unwrapped text length with no clamp to the container, and `VerticalScroll` is `overflow-x: hidden`. A 300-character question is a 300-column, 1-row label clipped at the right edge. The app was not run in this session; the failing test below is the reproduction.
- `questions.parse` (`devteam/questions.py:19`, join at line 38) joins continuation lines with a single space. One long string is the right input for a wrapping widget, so no change is needed in `questions.py`.
- `Note` (`tui.py:271`) uses `Label ... classes="question"` for a short fixed prompt. Fixing only the `Answers` question label (for example `Label(..., shrink=True)` there, or a CSS rule scoped to the Answers dialog) leaves `Note` untouched. A rule on `.question` globally would reach `Note`.
- Vertical limit: the real bound on the scroll area is the dialog (`max-height: 85%`, and `Vertical` is `overflow: hidden`), not the scroll area's `max-height: 30`. At `(80, 30)` the dialog is 25 rows, leaving roughly 13 rows for the scroll area after title, buttons and hint. Because the scroll area is `height: auto`, content taller than that is clipped by the dialog together with the buttons and hint, with no scrollbar. Wrapping makes this reachable with two long questions (each costs its wrapped lines plus 6 rows for the answer box). "Shown in full" is therefore only delivered if the scroll area is bounded by the dialog, so that it scrolls and the Save/Cancel buttons stay visible. This is in scope: it is the same symptom (a question cannot be read or answered) and the fix is small. It is stated as a criterion rather than put to the customer.
- Existing tests that use `Answers` (`test_answering_questions_then_moving_on_and_the_agent_resumes`, `tests/test_tui.py:379`) run at 120x40 with short questions. They must continue to pass.

What would change: `devteam/tui.py` only (CSS and/or the one `Label`), plus new tests in `tests/test_tui.py`. No change to parsing or to the files written by `questions.answer`.

Out of scope (noted, not unnoticed): other labels in these dialogs have the same non-wrapping behaviour: the item title header in `Answers` and `Note`, the `Note` description and hint, and the `Actions` warnings. The customer reported question text only. Do not extend the work to them; mention in the hand-off if the fix covers them incidentally.

Second, existing defect (fixed alongside, not part of the truncation): the scroll area is not bounded by the dialog, so Save and Cancel are expected to be pushed out of the dialog by enough ordinary short questions with no long text involved. By layout arithmetic (7 rows per short question), three short questions at `(80, 30)` need about 21 rows against about 13 available, and four at `(120, 40)` need about 28 against about 22. This is expected, not established: shell execution was refused in this session and in both earlier reviews. The implementer's recorded pre-fix output (see "Evidence workflow") is the confirmation. Wrapping makes it far easier to hit, and shipping wrapping without it would trade an unreadable question for an unreachable Save button, so it is fixed here. The `## Implementation` section must describe it as a separate defect, not as part of the truncation fix.

Evidence workflow: the workflow runs `implement` before `test`, the tester must not touch `tui.py`, and the runner writes the commit message itself, so "fails before the fix" can only be shown by recorded output. Before changing `tui.py`, the implementer runs `Answers` (an app using `Backlog.CSS`, under `run_test(size=...)`) at the fixtures of criteria 1, 4 and 5 and records under `## Implementation` the regions of the dialog, its `content_region`, the scroll area, the question labels, `#save`, `#cancel` and the hint label. The tester's tests assert the after-state only.

Risk to guard: the dialog is `height: auto`. Bounding the scroll area with `height: 1fr` or a fixed dialog height can make a one-question dialog fill 85% of the screen, or collapse the scroll area and hide the answer boxes. The dialog's size when the questions fit must stay as it is today (criterion 4).

Assumptions (not questions):

- Wrapping at word boundaries is enough. A word longer than the line (for example a long URL) is folded by Textual and must not be cut off; criterion 1 includes an unbroken 120-character token to check this.
- Questions taller than the visible area are reached by scrolling, provided the buttons stay visible.
- The dialog must not change size for questions that fit. The dialog height at `(120, 40)` with two short questions is expected to be 26 rows (2 title, 14 scroll area, 4 buttons, 2 hint, 4 border and padding) but was not run; the implementer records the actual value pre-fix, and the run wins over the arithmetic.

A CSS `height: 1fr` trial enlarged that fitting dialog to 34 rows and was discarded; the small resize handler satisfies the criteria without that change. The five-short-question tall-terminal fixture at `(120, 60)` retains its 42-row dialog and 30-row scroll area.

Added four focused layout tests in `tests/test_tui.py` covering horizontal wrapping (including the final word and the scrollbar-narrowed width), scrolling with visible controls, unchanged fitting layout, and the one-line `Note` prompt. These use real Textual widgets with the application's CSS and real repository rows.
