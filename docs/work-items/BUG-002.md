In the terminal UI, an item waiting on the customer at a `*-questions` step sometimes shows no "N unanswered questions" prompt and no "Answer N questions" option, even though the body holds unanswered questions. It is most common on the second round of questions, when the agent appends new questions to a body that already has answered ones.

## Analysis

### Cause (established from the customer's report and the STORY-006 run log)

The customer's answer to Question 1: STORY-006, second time at the answering step, offered no way to answer, only to move back to analysis; the first time (one question) it worked.

The run log `backlog/log/STORY-006/analysis-20261007T193118599409.log` shows the agent's edit for that round. It appended questions 2 to 5 each followed by an empty answer placeholder, in this shape:

```
2. <question text>

   **Answer:**

3. <question text>

   **Answer:**
```

`ANSWER` (`devteam/questions.py:9`) is `\s*>?\s*\**\s*Answer\b`, so `   **Answer:**` matches whether or not any text follows, and `parse` (`questions.py:35`) sets `answered = True`. Question 1 (answered) plus 2 to 5 (all "answered" by placeholder) gives zero unanswered, so `tui.rows` (`devteam/tui.py:83`) counts zero and the card (`tui.py:172`) and Actions menu (`tui.py:192`) show nothing. This matches the report exactly, including the first round working (that round had no placeholder). I have read the regexes by hand; I could not run the parser here (command execution was refused), so the implementer's first test should reproduce it.

Why the agent did it: `prompts/analysis.md:12` and `prompts/analysis/{architect,platform-engineer,quality-lead,product-owner}.md:12` say "the customer's reply appears / Answers appear beneath each question as `**Answer:** ...`", which reads as a template to copy. So the prompts were not ignored; they invite the placeholder.

The other round-two body, `analysis-20261007T200140371492.log` (Question 6), I did not inspect line by line; the current STORY-006 body shows question 6 parsed from a single continuous list with no placeholder in its final form, so it does not contradict the cause.

### What exists today

- `questions.parse` (`devteam/questions.py:19`) is the single source for the TUI count. `tui.rows` sums unanswered questions only when the step is human-owned; the card and Actions menu show the prompt only when that count is non-zero. The `Answers` screen (`tui.py:221`) lists the same unanswered items. A parser miss therefore means no prompt, no option and no message.
- `questions.answer` (`questions.py:42`) skips any question already marked answered, and otherwise inserts a new block `   **Answer:** first` plus further answer lines at three spaces after the question's `last_line`. With a placeholder present it would, if the question were treated as unanswered, insert a second marker after the empty one.
- A section opens on a line matching `## Questions` exactly (`SECTION`, anchored with `$`) and closes at any `#` or `##` heading (`HEADING`). `###` and deeper do not close it.
- A question is any line matching `QUESTION` (`\s{0,3}` then `N.`, `N)`, `-` or `*`). Later non-blank lines are continuation text of the current question unless they match `ANSWER`. Items at four or more spaces are already folded into the previous question.
- After a successful answer, `tui.answered` (`tui.py:555-558`) reopens `Actions` on the fresh row while the item is still at `answering`; `tests/test_tui.py:403-405` pins this and asserts the options are exactly `["answered", "withdraw"]`. At that moment unanswered is zero.
- Existing tests: `tests/test_tui.py` `QuestionParsing` (single round, one answered; `BODY` has `- Any budget?` at column 0 directly after question 2) and `tests/test_requests.py:152` (one question per role, appended to one list). `test_tui.py:186-187` answers with `"Friday.\nNo later."` and asserts the continuation at three spaces. None has an empty placeholder, a repeated heading or a variant heading.

### Further defects found by reading the code (secondary; the customer said to fix the over-counts here)

1. Over-count: a bullet or numbered line inside an answer is counted as a new unanswered question. `1. A?` / `   **Answer:** yes` / `   - detail` yields two questions. `answer()` indents multi-line answers three spaces, so a customer's list creates phantom questions.
2. Under-count (also gives "no prompt"): a variant heading (`## Questions (round 2)`, `## Questions for the customer`) fails `SECTION`, matches `HEADING` and closes the section; a `### Questions` after another `##` section is ignored.
3. Under-count: questions placed after another section without a new `## Questions` heading are ignored.
4. Over-count: sub-bullets inside a question (`   - option a`) at indent 0 to 3 are counted as questions.
5. False "answered": a continuation line starting "Answer options are:" marks the question answered, because `ANSWER` needs a word boundary, not a colon.
6. A repeated exact `## Questions` heading and a `### Questions` directly inside an open section work today. Not defects.

Real bodies in `backlog/requests/` parse correctly by reading. Multi-round bodies are in `backlog/stories/` (STORY-006 six questions, STORY-009 to 012); STORY-012 has a question directly after an answer with no blank line (line 99) and a prose paragraph at column 0 after the last answer (line 111). The backlog is its own git repository (`backlog/.git`); `git log -- backlog` in the code repository is empty by design. Neither the analyst nor the challenger could read its history, so fixtures use the working-tree bodies (criterion 9).

### What would change

Primary (the reported cause):

- `devteam/questions.py` `parse`: a question is answered only if text follows the colon on its `Answer:` marker line. A bare `**Answer:**`, `> **Answer:**` or `Answer:` with nothing after it is a placeholder and the question stays unanswered, whatever lines follow it (an agent's note or sub-bullet under a placeholder must not hide the question). `answer()` always writes the text on the marker line and all 19 answers in the real bodies have it there, so nothing needs the looser rule. A customer who hand-types an answer on the line below an empty marker is prompted again: visible and harmless, unlike a hidden question.
- `questions.answer`: for an unanswered question that has a placeholder marker line, write the answer on that line (`   **Answer:** first`) instead of inserting a second marker; further lines go beneath it, and any lines already beneath the placeholder stay in place after them. Continuation lines stay at three spaces, as today. Result: no duplicate markers, and `parse` then reports it answered.
- Prompts (`prompts/analysis.md` and `prompts/analysis/*.md`): add the sentence in criterion 7 so agents stop writing placeholders and nested lists.

Safety net (independent of cause):

- `devteam/tui.py`: a human-owned step that the item's workflow enters by a transition named `questions` (in `workflows/default.json` that is `answering`; no step-name matching) is a questions step. When it has zero unanswered questions, the card and the Actions dialog carry a plain label stating how many questions the body holds (criterion 6). The wording is true on the normal post-answer pass and useful when the parser has missed something. It is a label, not an option: options stay exactly `["answered", "withdraw"]`.

Parser tolerance (customer said to fix the over-counts here, Question 2):

- Section headings are unchanged (`## Questions` exactly). Secondary defects 2 and 3 were found by reading only; every questions heading in the backlog is exactly `## Questions`, the customer did not ask for variant headings, and a loose rule would turn `### Questions already settled` into prompted questions. They are left to the safety net (criterion 6(c)) and the prompt (criterion 7).
- Answer marker requires the colon: `**Answer:**`, `> **Answer:**`, `Answer:`. A line starting "Answer options" is question text.
- Nesting rule (fixes over-counts 1 and 4 in the parser, not only in prompts): the first list item in a section sets its base indent. A later list item indented deeper than the base is part of the current question or its answer, never a new question; an item at the base indent or shallower is a new question. So `   - option a` under a question, and `   - item` or `   1. item` in an answer, are not questions, whether written by an agent or by hand. Existing tests and real bodies use column 0 as the base, so they are unaffected.
- `answer()` keeps writing the marker line and continuation lines at three spaces. The nesting rule already stops a list inside an answer being counted, so no existing assertion changes.

### Decisions taken

- The cause is the empty answer placeholder; fixing it (criteria 1 to 3) is the primary work. The safety net and tolerant parser follow.
- The customer asked for the over-counts to be fixed here (Question 2); both are fixed in the parser by the nesting rule, and the prompt only reduces how often they arise.
- Only text on the marker line counts as an answer; no heading-rule change (challenge round three, findings 1 and 3). Under-counts 2 and 3 are not fixed in the parser and are not part of this item beyond the safety net.
- This replaces the earlier "any list item at indent 0 to 3 is a question": a question must now sit at the section's base indent. Chosen because it is the only rule that stops phantom sub-bullet questions regardless of who wrote them.
- Out of scope: changing how the runner or workflow routes `questions` steps.
